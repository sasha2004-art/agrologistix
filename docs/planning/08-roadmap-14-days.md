# Roadmap разработки на 14 дней

## 1. Цель и состав команды

Цель спринта — собрать демонстрационный MVP AgroLogistix, который проходит полный сценарий логиста:

`PIN -> ERP-состояние -> погода -> базовый расчёт -> стресс-событие -> пересчёт -> Было/Стало -> PDF/XLSX`.

| Роль | Зона ответственности | Рабочая директория |
| :--- | :--- | :--- |
| **Dev 1 — Backend / Math / DevOps** | FastAPI, SQLite, SQLModel, интеграции, солвер, экспорт, systemd, Nginx и CI | `backend/`, `.github/`, скрипты |
| **Dev 2 — Frontend / UI / Map** | Vue, Vuetify, Pinia, роутинг, карта, сценарии UI, печатный лист | `frontend/` |

Оба разработчика работают параллельно. Общие изменения ограничиваются API-контрактами, `.env.example`, корневыми CI-файлами и финальной интеграцией. Каждый такой файл изменяет только один назначенный разработчик.

## 2. Результат к концу 14-го дня

К концу спринта должны быть готовы:

- публичный лендинг `/` с переходом на экран входа и вход по 6-значному PIN;
- dashboard логиста без вертикального скролла на desktop-разрешении;
- данные двух складов, трёх культур, пяти клиентов и трёх грузовиков;
- CRUD или редактирование необходимого MVP-состояния ERP;
- переключение погодных режимов `normal`, `heatwave_35c`, `heavy_rain`;
- расчёт маршрутов с ограничениями вместимости, типа дороги, состояния машины и остатков склада;
- формула свежести и финансовые метрики TCO;
- гарантированно разрешимый сценарий с `unmet_kg`, когда транспорта не хватает;
- пересчёт после доставки конкретной заявки (`order_id`), поломки грузовика или изменения цены;
- визуальное сравнение «Было / Стало»;
- Mapbox-карта с fallback при недоступном внешнем API;
- печать маршрутного листа через browser print и скачивание XLSX;
- CI с линтингом, type-check, сборкой и проверкой лимита 500 строк;
- воспроизводимый demo-сценарий без ручного редактирования базы.

## 3. Правила параллельной работы

1. **Dev 1 не изменяет `frontend/`, Dev 2 не изменяет `backend/`.** Исключения заранее согласуются для контрактов и конфигурации.
2. API-контракт фиксируется в конце Day 1. После этого breaking changes допускаются только через короткую совместную синхронизацию.
3. Пока API не готов, Dev 2 работает на typed mock-адаптере с теми же DTO и URL.
4. Состояние сценария имеет один источник правды: действия логиста (`delivered`, `broken`, изменение цены и погодный override) сначала сохраняются через API в SQLite. `POST /solver/optimize` не принимает повторяющие эти изменения поля, а читает актуальное состояние БД и при `what_if` сравнивает его со слепком `baseline_run_id`.
5. Каждый рабочий день завершается короткой проверкой: что готово, что заблокировано, какой контракт изменился.
6. Коммиты — небольшие и тематические, в формате Conventional Commits. Примеры: `feat(api): add erp state endpoint`, `feat(ui): add pin login screen`.
7. Любой кодовый файл (`.py`, `.ts`, `.vue`) должен оставаться не длиннее 500 строк. Большие компоненты декомпозируются сразу.
8. Внешние API не должны блокировать демо: Open-Meteo и Mapbox имеют таймаут 1.5 секунды и локальные fallback/cache.

## 4. Контракт синхронизации

### Обязательные endpoint'ы MVP

| Метод и путь | Назначение | Готовность для фронтенда |
| :--- | :--- | :--- |
| `GET /api/v1/health` | Проверка сервера без авторизации | Day 2 |
| `POST /api/v1/auth/verify-pin` | Проверка PIN, возврат роли и `is_admin` | Day 2 |
| `GET /api/v1/erp/state` | Полное состояние складов, заявок, клиентов и автопарка | Day 4 |
| `PATCH /api/v1/erp/orders/{id}` | Изменение цены и статуса конкретной заявки | Day 4 |
| `PATCH /api/v1/erp/trucks/{id}` | Перевод машины в `active` / `broken` | Day 4 |
| `PATCH /api/v1/erp/stocks/{id}` | Изменение остатка, если требуется демо-сценарием | Day 4 |
| `GET /api/v1/weather/current` | Текущая погода и активный режим | Day 5 |
| `POST /api/v1/weather/override` | Выбор стресс-пресета | Day 5 |
| `POST /api/v1/solver/optimize` | Базовый или повторный расчёт | Day 8 |
| `GET /api/v1/export/run/{run_id}/xlsx` | Скачивание XLSX | Day 10 |
| `POST /api/v1/system/reset-demo` | Сброс seed-данных, только admin | Day 3 |

### Минимальные DTO

Типы должны совпадать в `backend/app/schemas/` и `frontend/src/shared/types/domain.ts`.

```text
AuthResponse:
  role: "dispatcher" | "admin"
  is_admin: boolean
  access_pin_valid: boolean

SolverRequest:
  mode: "baseline" | "what_if"
  baseline_run_id?: number

SolverResponse:
  run_id: number
  parent_run_id?: number
  routes: Route[]
  metrics: Metrics
  warnings: Warning[]
  comparison?: ComparisonDelta

Metrics:
  total_tco_rub: number
  total_trip_cost_rub: number
  total_spoilage_loss_rub: number
  total_unmet_penalty_rub: number
  expected_net_profit_rub: number
  avg_freshness_pct: number
  shipped_kg: number
  unmet_kg: number
```

Поля JSON передаются в `snake_case`; на фронтенде типы и адаптеры явно описывают преобразование, если оно понадобится.

**Правило состояния для `what_if`:** Dev 2 сначала вызывает соответствующий `PATCH` для изменения заявки, машины или статуса доставки, дожидается успешного ответа и затем вызывает `POST /solver/optimize` с `{ "mode": "what_if", "baseline_run_id": 1 }`. Backend читает актуальные `ClientOrder`, `Truck` и связанные сущности из SQLite; `SimulationRun` хранит неизменяемый слепок базового расчёта. Для доставки используется уровень заявки (`order_id`), а не клиента: один клиент может иметь несколько культур и рейсов.

## 6. Ежедневный ритм и контрольные точки

- **Начало дня, 10 минут:** определить одну главную цель дня и проверить блокеры.
- **Середина дня, 5 минут:** сверить изменения API и состояние интеграции.
- **Конец дня, 15 минут:** запустить проверки своей зоны и записать результат.
- **После каждого контракта:** Dev 1 публикует пример JSON, Dev 2 проверяет его typed-клиентом.
- **Для сценария `what_if`:** сначала подтверждённый PATCH и обновление ERP-state, затем запрос solver с `baseline_run_id`; не дублировать состояние в двух источниках.
- **После каждого merge:** запускать CI; неисправный `main` не использовать как основу для новой функциональности.

Минимальный локальный набор проверок:

```bash
# Backend
ruff check backend/
ruff format --check backend/
pytest backend/tests/
bash scripts/check_loc.sh

# Frontend
npm run lint --prefix frontend
npm run type-check --prefix frontend
npm run build --prefix frontend
```

## 7. Definition of Done

Задача считается завершённой, когда:

- код находится в правильной зоне ответственности и не нарушает лимит 500 строк;
- есть обработка loading, empty, error и успешного состояния;
- API имеет response model и проверку авторизации;
- бизнес-правило покрыто тестом или зафиксировано в проверяемом demo-сценарии;
- внешний сервис имеет таймаут и fallback/cache, если он участвует в основном потоке;
- линтеры, type-check, сборка и тесты проходят;
- изменение проверено на реальном контуре второго разработчика;
- нет секретов, временных mock-данных или ручных шагов, необходимых для запуска демо.

## 8. Резерв и приоритеты при отставании

Если команда отстаёт, порядок сохранения объёма такой:

1. Сохранить авторизацию, ERP, solver, what-if и карту.
2. Сохранить PDF через browser print и базовый XLSX.
3. Оставить Open-Meteo и Mapbox только с качественным fallback, если интеграции не успевают.
4. Убрать второстепенные визуальные эффекты и редкие CRUD-сценарии.
5. Не убирать always-feasible solver, ограничения грунтовки, фиксацию доставленных точек и метрики TCO: это основная демонстрационная ценность продукта.

## 9. Ограничения MVP, которые не должны попасть в работу спринта

В этот roadmap не входят GPS/ГЛОНАСС-трекинг, OAuth2/SSO, интеграция с 1С, автоматическое извлечение грунтовых дорог из OSM, 3D-укладка паллет и сложная биохимическая модель порчи. Эти функции не должны вытеснять обязательный end-to-end сценарий MVP.
