# Консолидация рейсов: одна машина на несколько магазинов

**Статус:** план (не реализовано)
**Роль:** Dev 1 (Backend / Math)
**Связанные документы:** `01-prd.md` (§2, §4), `02-trd.md` (§3, §5.2), `06-tasks.md` (`TASK-07`),

## 1. Проблема

Требование логиста: **если одна машина может за один выезд привезти товар в 3 магазина
(хватает грузоподъёмности, товар есть на базе, рефрижератор и погода позволяют довезти
свежим) — едет одна машина. Вторую подключаем только если первая не справляется**
(нет нужного продукта на её складе, не хватает вместимости, грунт/реф не подходят).

Сейчас мультистоповые рейсы технически есть (`build_route` + `two_opt_order`), но
аллокация `allocate_loads` распределяет заказы **по отдельным заявкам**, не пытаясь
держать магазин на одном рейсе и не экономя на числе рейсов.

### 1.1. Измерения на текущем seed (погода `normal`, 9 заказов, 11 000 кг)

| Машина | Стопов | Клиентов | Кг | Загрузка | Пробег | Время в пути |
|---|---|---|---|---|---|---|
| 1 (Volvo, асфальт) | 2 | 2 | 2 200 | 11 % | 114.5 км | 91.6 мин |
| 2 (ГАЗон, реф + грунт) | 5 | 4 | 5 600 | 93 % | 128.2 км | 153.8 мин |
| 3 (КАМАЗ, грунт, без рефа) | 2 | 2 | 3 200 | 32 % | 110.3 км | 94.6 мин |

* Рейсов: **3** (нижняя граница — 2, потому что три грунтовые заявки требуют машины с
  `can_use_dirt`, а еврофура на грунт не поедет).
* **4 из 5 клиентов** обслуживаются двумя машинами: визиты по клиентам `{1: 2, 2: 2, 3: 2, 4: 2, 5: 1}`.
* Заказы **одного клиента** (одинаковые координаты, например Боровск №5 и №6) попадают на
  разные машины — две поездки туда, где хватило бы одной.
* Для сравнения: при малом спросе (только 3 томатных заявки трёх разных клиентов) солвер
  сам строит **1 рейс с 3 остановками** — значит, механика мультистопа работает, ломается
  именно выбор распределения при полной загрузке.

### 1.2. Почему так происходит

1. **Прокси-стоимость вместо фактической.** В MILP цена доставки килограмма считается так
   (`backend/app/services/solver_allocation.py`, `unit_cost_rub`):

   ```
   trip_share = cost_per_km · distance(склад, клиент) / requested_kg
   unit_cost  = spoilage_per_kg + trip_share
   ```

   Километры не делятся между заказами, которые могли бы ехать в одном рейсе, а время и
   свежесть считаются по прямому плечу «склад → клиент», без учёта detour через другие
   остановки. Из-за этого три отдельные машины в модели могут выглядеть дешевле одного
   рейса с тремя остановками, хотя фактический TCO у них хуже (дороже `fixed_trip_cost_rub`,
   больше суммарный пробег).
2. **Нет ограничения «магазин — один рейс».** В MILP переменная `x[k, o]` привязана к
   заявке, а не к клиенту, поэтому два заказа одного клиента спокойно уезжают на разных
   машинах.
3. **Нет ограничений рейса** сверх вместимости и стока: ни лимита остановок, ни лимита
   времени смены, ни обязательного порога свежести на последней точке.
4. **Нет шага улучшения после роутинга.** `build_route` строит маршрут для заданного
   набора заказов, но никто не проверяет альтернативу «слить два рейса в один» по
   фактическому TCO.

### 1.3. Что уже работает и надо сохранить

* Мультистоп и порядок объезда: nearest-neighbour + 2-opt (`solver_routing.py`).
* Груз берётся только со склада базы машины (`truck.warehouse_id`), грунт и реф — жёсткие
  ограничения (`truck_can_serve_order`).
* Если на складе базы нет продукта, солвер отправляет машину другого склада — проверено:
  при обнулении томатов в Обнинске заказ уехал одной машиной со склада Детчино.
* Свежесть считается по накопленному времени с учётом рефа, дождя и грунта
  (`freshness_math.py`), потери входят в TCO.
* Always-feasible: недовоз — slack-переменная со штрафом, 500-х нет.

## 2. Целевое поведение (правила приёмки)

| Ситуация | Ожидаемое решение |
|---|---|
| Вместимость, сток, реф/погода, свежесть и лимит времени позволяют | **1 рейс, несколько магазинов** в одном выезде |
| Все заказы одного клиента помещаются в один рейс | заказы клиента **не дробятся** между машинами |
| Не хватает вместимости одной машины | добавляется вторая машина (сначала та же база) |
| На складе базы нет нужного продукта | рейс от другой базы (машина другого склада), без «пустого» рейса |
| Грунтовая точка, а машина без допуска | берётся dirt-машина (`can_use_dirt`) |
| Жара/дождь и нет рефа | берётся реф; если рефов нет — точка помечается предупреждением, потери входят в TCO |
| Длинный detour портит свежесть ниже порога | точку переносят в другой рейс/склад или помечают недовозом |

Целевая функция остаётся TCO-минимумом (PRD §2), но считается по **фактическому маршруту**,
поэтому консолидация становится выгодной там, где она действительно дешевле.

## 4. Алгоритм

Пайплайн: **черновая аллокация → построение рейсов → локальный поиск по фактическому TCO → метрики**.

### 4.1. Группировка заказов клиента в MILP

Ввести бинарную переменную `z[k, c] ∈ {0, 1}` — «машина `k` обслуживает клиента `c`»:

```
Σ_k z[k, c] = 1                    для каждого клиента c            (мягко/жёстко)
x[k, o] ≤ requested_kg[o] · z[k, c(o)]                              (связка)
```

* Жёсткий вариант (равенство) даёт правило «магазин — один рейс»; если это делает задачу
  невыполнимой (не хватает вместимости/стока), MILP сам вернёт недовоз — тогда сработает
  fallback: `Σ_k z[k, c] ≤ 2` плюс `solver_client_split_penalty_rub` в целевой функции.
* Размер задачи растёт на `машины × клиенты` бинарных переменных (на текущем seed 15) — для
  HiGHS это доли миллисекунды в рамках лимита 1.0 с.
* Дополнительно: сортировка greedy-fallback (`solver_allocation.py`) уже группирует по
  приоритету `penalty · kg`; добавить вторичный ключ `client_id`, чтобы заказы клиента
  попадали в одну машину и в fallback-пути.

### 4.2. Ограничения рейса

В `build_route`/после построения проверять и учитывать:

* `len(stops) ≤ solver_max_stops_per_trip`;
* `eta_minutes[-1] / 60 ≤ solver_max_trip_hours`;
* `expected_freshness` каждой остановки ≥ `solver_min_last_stop_freshness` (и на последней,
  и промежуточных — иначе груз у части клиентов приедет «на грани»);
* при превышении — заказ выносится из рейса и передаётся в improve-этап (другая машина /
  другой склад), в крайнем случае — недовоз с warning `trip_limit_exceeded`.

### 4.3. Локальный поиск по фактическому TCO (`solver_improve.py`)

После чернового плана считаем **фактический** TCO (полный `build_route` + `_collect_metrics`)
и улучшаем его локальным поиском с бюджетом времени:

Операторы (в порядке убывания отдачи):

| Оператор | Действие | Проверки |
|---|---|---|
| `merge(a, b)` | все заказы рейса `b` → в `a`, рейс `b` исчезает | вместимость, сток по складу `a`, грунт, реф, лимиты 4.2 |
| `relocate_client(c)` | собрать все заказы клиента `c` в один рейс | то же |
| `move(o, a→b)` | перенести одну заявку | то же |
| `swap(a, b)` | обменять заявки между рейсами | то же |
| `reorder(a)` | повторить 2-opt после изменений | — |

Критерий приёмки хода: `TCO_new < TCO_old − ε`, где `TCO` включает стоимость рейсов,
потери от порчи и штраф за недовоз (+ штраф за дробление клиентов). Tie-break: меньше
рейсов → выше средняя свежесть → меньше суммарный пробег.

Псевдокод:

```python
plan = build_routes(milp_allocation)
best = tco(plan)
while time_left():
    for candidate in generate_neighbours(plan):   # merge, relocate, move, swap
        if not feasible(candidate):
            continue
        score = tco(candidate)
        if score < best - EPSILON:
            plan, best = candidate, score
            break
    else:
        break
```

План маленький (≤ 3 машины, ≤ 9 заказов), поэтому полный пересчёт фактического TCO на
каждом ходе укладывается в бюджет 0.7 с вместе с MILP; при росте данных — ограничить
число соседей и глубину (beam width), сохранив лимит `SOLVER_TIME_LIMIT_SEC`.

Результат: `AllocationResult.method = "milp" | "milp+improved" | "greedy" | "greedy+improved"`.

## 7. Тесты и критерии приёмки

Новые тесты (`backend/tests/test_solver_consolidation.py`):

1. **Три магазина — один рейс.** Три заявки разных клиентов, товар на одном складе,
   вместимость и погода позволяют → ровно 1 рейс, 3 стопа, все три клиента.
2. **Магазин не дробится.** Два заказа одного клиента при достаточной вместимости → оба в
   одном рейсе (проверка `split_clients == 0`).
3. **Нет товара на базе.** Томаты отсутствуют на складе 1 → рейс уходит со склада 2; лишний
   «пустой» рейс не создаётся.
4. **Fallback на вторую машину.** Спрос превышает вместимость первой машины → добавляется
   вторая (реквизит: ни один рейс не превышает `capacity_kg`).
5. **Полный seed.** Рейсов не больше 3 (цель — 2), `split_clients == 0` при нормальной
   погоде, инварианты сохраняются (баланс спроса, сток, грунт, свежесть).
6. **Лимиты рейса.** При `max_stops = 3` четвёртая точка уходит в другой рейс, появляется
   warning `trip_limit_exceeded`; при `max_trip_hours` — то же по времени.
7. **Свежесть.** Жара без рефа даёт потерю свежести ниже порога → такой рейс не выбирается
   (или включается недовоз с `freshness_risk`).
8. **What-if.** Сломанная машина: её заказы переезжают в оставшиеся рейсы (merge), а не
   порождают новый рейс, пока хватает вместимости и стока.
9. **Производительность и детерминизм.** Два одинаковых расчёта дают один план; время
   `/solver/optimize` ≤ 1.5 с на seed.
10. **Регрессия.** Прогон `test_solver_invariants.py` и `test_solver_constraints.py` после
    включения improve-этапа.

пересчитываются после смены алгоритма; добавить сценарий «3 магазина за 1 рейс».
